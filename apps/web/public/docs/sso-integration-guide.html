How it works

Your application never sees a TatvaOS password. When a person needs to sign in, your application sends their browser to TatvaOS. TatvaOS signs them in if they are not already, asks them once whether your application may receive their name, work email address and organisation, and sends the browser back to your application with a one-time code. Your application's server exchanges that code for an ID token that says who the person is, an access token for the userinfo endpoint, and, if you asked for it, a refresh token so the person stays signed in.

If the organisation removes the person from TatvaOS, or suspends them, or revokes your application, their tokens stop working at their next use. That is the reason organisations connect applications this way instead of keeping separate passwords in each one.

Registering the application

An organisation administrator does this in TatvaOS under Organisation → Applications → New application. They need three things from you:

WhatWhat to give them
NameWhat people will see on the consent screen, for example Payroll.
Redirect URIsThe exact https:// address TatvaOS returns people to after sign-in — your application's callback. One per line. Matched character for character: no wildcards, and a trailing slash or a query string counts. http://localhost and http://127.0.0.1 are allowed for an application running on a developer's own machine.
Server application?Yes if your application has a server that can keep a secret (a web application, a backend). It receives a client secret. No if it runs entirely on a phone or in a browser and cannot keep a secret; it proves itself with PKCE alone.

TatvaOS then shows the administrator a client id (starts with tos_) and, for a server application, a client secret (starts with toss_). The secret is shown once. It cannot be shown again; if it is lost, the administrator registers the application again and you update your configuration with the new client id and secret.

Rules every application must follow

  • Authorization code flow only. response_type=code. Implicit and hybrid flows are refused.
  • PKCE with S256, always — for server applications too. A request without code_challenge, or with code_challenge_method=plain, is refused.
  • Redirect URIs match exactly. Register the precise callback address. https://app.example.com/cb and https://app.example.com/cb/ are different addresses.
  • The secret stays on your server. Never in a browser, a mobile app, a repository or a log.
  • Send state and nonce and check both when the browser comes back.
  • Check the organisation. Every token carries tid, the organisation's id. If your application serves one organisation, refuse a token whose tid is not that organisation's.

The flow, request by request

1. Send the person to TatvaOS

Generate a random code_verifier (43 to 128 characters), compute code_challenge = base64url(sha256(code_verifier)), generate a random state and nonce, remember all three in the person's session, and redirect the browser to:

https://core.tatvaos.com/oauth/authorize
  ?response_type=code
  &client_id=tos_…
  &redirect_uri=https%3A%2F%2Fapp.example.com%2Fauth%2Fcallback
  &scope=openid%20profile%20email%20offline_access
  &state=…
  &nonce=…
  &code_challenge=…
  &code_challenge_method=S256

If the person is not signed in to TatvaOS they sign in there, with two-step verification if they use it. The first time your application asks for them, TatvaOS shows a consent screen naming your application and what it will receive. After that, TatvaOS remembers the answer.

2. Receive the code

TatvaOS sends the browser to your redirect URI:

https://app.example.com/auth/callback?code=…&state=…&iss=https%3A%2F%2Fcore.tatvaos.com%2F

Check that state equals the one you stored, and that iss is https://core.tatvaos.com/. If the person cancelled, or is not allowed, you receive error=access_denied instead of a code.

The code lives 60 seconds and works once. Exchange it straight away.

3. Exchange the code for tokens

From your server, a POST to the token endpoint. A server application sends its secret; a phone or browser application sends only its client id.

curl -X POST https://core.tatvaos.com/api/oauth/token \
  -d grant_type=authorization_code \
  -d code=… \
  -d redirect_uri=https://app.example.com/auth/callback \
  -d client_id=tos_… \
  -d client_secret=toss_… \
  -d code_verifier=…

The secret may also be sent as HTTP Basic authentication (client_id:client_secret). The response:

{
  "access_token":  "…",
  "token_type":    "Bearer",
  "expires_in":    600,
  "id_token":      "eyJhbGciOiJSUzI1NiIsImtpZCI6…",
  "refresh_token": "…",
  "scope":         "openid profile email offline_access"
}

refresh_token is present only when you asked for offline_access. The access and refresh tokens are opaque strings; do not try to decode them. The ID token is a signed JWT, described next.

4. Read who the person is

Verify the ID token (below) and read sub, email, name and tid from it. Or call userinfo with the access token:

curl https://core.tatvaos.com/api/oauth/userinfo \
  -H "Authorization: Bearer …"

{ "sub": "…", "tid": "…", "name": "Asha Rao", "email": "asha@example.com", "email_verified": true }

Userinfo answers 401 the moment the person is suspended, removed, or your application is revoked — it checks on every call.

The ID token and its claims

The ID token is a JWT signed with RS256. Verify its signature against the key in the key set whose kid matches the token's header; then check the claims. Every OpenID Connect library does this for you when given the issuer.

ClaimMeaning
isshttps://core.tatvaos.com/. Must match exactly.
audYour client id. Must match.
subThe person's permanent id. Use this as the key for the person in your application. Never the email, which can change.
tidThe organisation's id. The same for everyone in that organisation. Check it if your application serves specific organisations.
email, email_verifiedThe person's work address, with email scope. email_verified is true when the address is on a domain the organisation has proved it owns.
nameThe person's display name, with profile scope.
nonceThe nonce you sent. Must match.
exp, iatThe ID token lives 5 minutes. Use it to establish the person's session in your application, then rely on your own session.
Keys rotate. TatvaOS rotates its signing key every 90 days and publishes the retired key for one more day. Fetch the key set by kid and re-fetch it when you meet a kid you do not know; do not pin a key.

Staying signed in: refresh tokens

With offline_access, the token response includes a refresh token. Access tokens live 10 minutes; when one expires, exchange the refresh token for a new set:

curl -X POST https://core.tatvaos.com/api/oauth/token \
  -d grant_type=refresh_token \
  -d refresh_token=… \
  -d client_id=tos_… \
  -d client_secret=toss_…

Each use returns a new refresh token and retires the old one. Store the new one every time. Using a retired refresh token again revokes the whole chain — TatvaOS treats a second use as a sign that the token was copied — and the person has to sign in through TatvaOS again. A refresh token lives 14 days from its issue if unused; every refresh re-checks that the person and the organisation are still active and that your application is still allowed.

Using a library

You do not need to implement the requests above by hand. Give your framework's OpenID Connect client the issuer, the client id, the secret and the scopes, and make sure PKCE is on. The shape, in three common stacks:

ASP.NET Core

builder.Services.AddAuthentication(options => {
        options.DefaultScheme = "Cookies";
        options.DefaultChallengeScheme = "oidc";
    })
    .AddCookie("Cookies")
    .AddOpenIdConnect("oidc", options => {
        options.Authority = "https://core.tatvaos.com";
        options.ClientId = "tos_…";
        options.ClientSecret = "toss_…";          // from configuration, never in code
        options.ResponseType = "code";
        options.UsePkce = true;
        options.Scope.Clear();
        foreach (var s in new[] { "openid", "profile", "email", "offline_access" }) options.Scope.Add(s);
        options.CallbackPath = "/auth/callback";  // register https://your-app/auth/callback
        options.SaveTokens = true;
    });

Node.js (openid-client)

import * as client from 'openid-client';

const config = await client.discovery(
  new URL('https://core.tatvaos.com'), 'tos_…', process.env.TATVAOS_CLIENT_SECRET);

// 1. redirect
const codeVerifier = client.randomPKCECodeVerifier();
const url = client.buildAuthorizationUrl(config, {
  redirect_uri: 'https://app.example.com/auth/callback',
  scope: 'openid profile email offline_access',
  code_challenge: await client.calculatePKCECodeChallenge(codeVerifier),
  code_challenge_method: 'S256',
  state, nonce,
});

// 2. callback
const tokens = await client.authorizationCodeGrant(config, new URL(req.url, 'https://app.example.com'), {
  pkceCodeVerifier: codeVerifier, expectedState: state, expectedNonce: nonce,
});
const claims = tokens.claims();   // claims.sub, claims.email, claims.tid

Python (Authlib, Flask)

oauth = OAuth(app)
oauth.register(
    name='tatvaos',
    server_metadata_url='https://core.tatvaos.com/.well-known/openid-configuration',
    client_id='tos_…',

# redirect: oauth.tatvaos.authorize_redirect(url_for('callback', _external=True))
# callback: token = oauth.tatvaos.authorize_access_token(); user = token['userinfo']

Lifetimes, limits and what revocation does

ItemValue
Authorization code60 seconds, single use
ID token5 minutes
Access token10 minutes, checked on every call
Refresh token14 days, rotated on every use
Token endpoint120 requests a minute per address
Authorization endpoint60 requests a minute per address

When an administrator revokes your application, new sign-ins are refused, its refresh tokens stop working, and its access tokens are refused on their next call. When a person removes their consent on their account page, the same happens for that person alone, and the next sign-in asks them again. When a person is suspended or removed, their refresh and access tokens stop at their next use.

What revocation cannot do. An ID token already delivered stays valid until it expires, which is why it lives five minutes. And your application's own session — the cookie you set after sign-in — is yours; TatvaOS cannot end it. People already signed in to your application stay signed in there until your application signs them out. If your application must react to a revocation quickly, keep your own sessions short or call userinfo when it matters.
Browser-only applications. An application that runs entirely in the browser with no server of its own would need the token endpoint to accept cross-origin requests, which TatvaOS does not offer today. Give such an application a small backend that performs the exchange, or ask your TatvaOS contact about the timeline.

Security checklist

  • Register the exact callback address, and only https:// outside a developer machine.
  • Keep the client secret in configuration on the server. Never ship it to a browser or a phone; never commit it; never log it.
  • Use PKCE with S256 on every request, and a fresh state, nonce and verifier each time.
  • Verify the ID token: signature by kid, iss, aud, nonce, exp.
  • Key the person on sub, never on email.
  • Check tid against the organisations your application serves.
  • Store each new refresh token as it arrives; never reuse a retired one.
  • Treat 401 from userinfo and invalid_grant from refresh as "sign in again", not as transient errors.
  • Do not log codes, tokens, verifiers, or the full callback URL.

Testing without writing code

To see the sign-in leg work before your code exists, register a test application with the redirect URI https://oidcdebugger.com/debug and Server application unticked, then at oidcdebugger.com enter the authorize URI https://core.tatvaos.com/oauth/authorize, your client id, scope openid profile email, response type code, and tick Use PKCE. Send the request: you will see the TatvaOS consent screen, then a page showing the code and your state. Revoke the test application afterwards. The debugger shows the code only; the code-for-tokens exchange is your server's part.
