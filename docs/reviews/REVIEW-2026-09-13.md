## 3. The deploy that did not land — READ THIS FIRST, Core

Three attempts to deploy `6f0ded8`, three failures, all different:

1. **Branch guard.** The production checkout was on `feat/csv-import-people`.
   `deploy.sh` refused. Correct. Fixed by hand:
   `git checkout -B main origin/main`. Fourth wrong-branch checkout in a week;
   the guard has stopped every one.
2. **`dial tcp …:22: i/o timeout`.** GitHub's runner could not reach the box
   for 30 s. Transient — the next attempt connected.
3. **`[FAIL] cannot read BUILD_SHA from the running web container`.** The
   deploy ran for four minutes, one step failed, this one. Then measured:
   `docker compose ps web` shows `tatvaos-web-1` **created 13 hours ago**. The
   containers were not replaced.

**What is known:** production serves the previous build; the proof step
correctly refused to call this deploy a success; the new migration
(`20260910-entitlement-overrides.sql`) may or may not have been applied —
**check `\dt core.entitlement_overrides` before assuming either way.**

**Measured, 02:00 IST:** `docker inspect … tatvaos-web-1 | grep '^BUILD_SHA'`
printed **nothing**. The running web container has **no `BUILD_SHA` in its
environment at all** — not empty, absent. So the container serving production
was built by something that never passed the build arg, and the proof step
cannot pass against it no matter what is deployed, until `web` is genuinely
rebuilt and recreated with the arg set.

**What is not known, and is Core's first job:** why tonight's deploy did not
recreate `web`. A changed `ARG BUILD_SHA` → `ENV BUILD_SHA` should produce a
new image layer and force recreation; it did not happen. Either the build did
not run to completion (the log will show), or `up -d` was not reached, or the
compose invocation that built is not the one that checked. The full run log is
saved as `deploy-34716535090.log` in the integration checkout (untracked).
Read it before touching anything.

**Do not "fix" this by adding `--force-recreate` blindly.** Read the comment
block above the check in `deploy.sh` (search `cannot be proven to have
landed`) — it records the incident that made this check exist. Find out why
recreation did not happen, then decide.

Also found on the production checkout, untracked: `infra/docker/.env.backup-…`
and `.env.bak-…` — **plaintext copies of every production secret on disk** —
and the file named `main` that caused the 3 Sept "ambiguous argument"
failure. Core's handover §3 warned about the first shape. Remove both, after
confirming the live `.env` is intact.
