## What I sent back

**To Connect — recording sharing is half-built, and the half that is missing
is the half that matters.**

A host can create a share link, name people, set an expiry, revoke it, and an
admin can flip the "allow public links" switch. All of that is wired up and
live. **Nothing reads any of it.** The code that decides whether someone is
allowed to open a recording never asks "does a share permit this person?" —
I checked the file that owns that decision and it contains no mention of
sharing at all.

So as it stands: a host shares a recording, gets a link, sends it to a
customer, and the customer cannot open it. The buttons work. The link does
not. This needs to be fixed or hidden before anyone finds it the hard way.

**Two more faults on that same path, which will both fire the day it is
wired up.** I'm flagging them now so they aren't found twice:

1. The database function that turns a link into a recording had its
   permissions taken away from everyone and never given back to the
   application's account. First public link opened = "permission denied".
   One missing line in the migration.
2. Reading the link's password is done through a query that is locked to one
   organisation — but a person clicking a link isn't signed in and has no
   organisation. That query will return nothing, so **the correct password
   will be rejected every time.** The migration's own notes describe this
   exact trap and fix it for writing; the reading side was missed.

**Small one, same file:** two notes stored in the live database point readers
at a file called `20260826-connect-recording-shares.sql`. There is no such
file — it was renamed to `20260908-b-`. Whoever reads that note next will go
looking for something that isn't there.

## Needs Amit

**Recording sharing: pull the buttons, or push to finish it?**

- **Pull them** — hide the share controls until the reading side is built.
  Costs: Connect loses visible progress, and whoever you demoed this to sees
  it disappear. Gains: nobody sends a customer a link that doesn't open.
- **Leave them and rush the rest** — costs roughly the same effort either way,
  but every day in between is a day a host can hand out a dead link and
  conclude the product is broken.

**I recommend pulling them.** A feature that is invisible is a roadmap item.
A feature that is visible and silently fails is a support ticket and a lost
customer, and it teaches people the suite is unreliable — which is much more
expensive to undo than a missing button.

## Quiet risks

- **My review has a blind spot until the sandbox is fixed.** I can read files
  but I cannot compare versions, so I can't see what changed, only what is
  there now. Treat the next few notes as spot-checks, not full reviews.
- **One migration file still uses the old numbering** (`0032-mail-categories`)
  instead of a date. It is harmless today — I checked what it depends on — but
  the whole point of the date rule is that the next person who copies the old
  style breaks a fresh install, which is a bug that only shows up when you
  restore from a backup. Worth renaming while it is still free.
