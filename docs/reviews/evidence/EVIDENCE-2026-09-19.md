### SMS: consent, retention, error handling — the honest state

**Consent.** There is no consent checkbox and no stored record of consent. The door shows this sentence under the number field: *"An Indian mobile number. We text it a code so you are counted once, however often you rejoin. The number itself is not kept and nobody in the meeting sees it."* The guest then presses "Send code" themselves. Whether that is sufficient notice under the DPDP Act for a guest who is not the customer's employee is **not something I am qualified to rule on**; it needs Mr. Singh or counsel.

**What is stored, and for how long.**

| Data | Where | Retention |
|---|---|---|
| The phone number itself | **Not in the database.** | — |
| HMAC of the number, bound to the meeting | `connect.participants.guest_phone_hash`, `connect.guest_otps.phone_hash` | **As long as the meeting row exists. There is no sweeper.** `guest_otps` cascades when a meeting is deleted; nothing deletes meetings on a schedule. **This is an open gap.** |
| HMAC of the code | `connect.guest_otps.otp_hash` | Nulled when used or after 5 wrong guesses; the row stays (it carries the send count) |
| The number, in transit | API process memory; the SMS provider (Infobip or MSG91) | The provider keeps its own delivery logs under its own policy. We do not control that |
| The pass | The guest's browser, localStorage | 24 hours validity; the entry itself stays until cleared |

**Defect D1 — must be fixed before merge.** `apps/api/Shared/Notify/Notify.cs` (existing code, not written in this PR) logs the **full phone number** on every failure path: `"SMS not configured; OTP for {Phone} not sent"`, `"Infobip rejected send to {To}: …"`, `"MSG91 send to {To} failed"`. Until today the only numbers reaching it were our own signed-in users'. PR 184 sends strangers' numbers through it. So the PR description's sentence "the number is never stored" is **false for server logs**, and the sentence shown to the guest overstates. Proposed fix: mask to the last four digits inside `SmsSender`'s log lines (a Core file; one-line changes), and add a check that greps the API log for the test number after a failed send. I have not made this change.

**Defect D2 — the key.** The HMAC key is derived from the JWT signing key. Rotating that key orphans every stored hash and pass; guests would simply verify again, but a returning guest would become a second row. Acceptable or not is Mr. Singh's call.

**Error handling, as built:**

| Situation | Answer | What the guest sees |
|---|---|---|
| Not an Indian 10-digit mobile number | 400 | "Give a 10-digit Indian mobile number." |
| Asked again within 45 s | 429 | "A code was just sent. Wait a moment…" |
| Sixth text to one number for one meeting | 429 | "Too many codes have been sent to this number…" |
| Seventh request from one address in 10 min | 429 (rate limiter) | generic |
| SMS provider fails | 502, JSON `error` field | "The code could not be sent. Try again in a minute." |
| Wrong / expired / used / never-sent code | 400, one sentence for all four | "That code is not right, or it has expired…" |
| Five wrong guesses | code dies | same sentence; a new code must be requested |
| Meeting-wide ceiling of distinct numbers (2000) | 404 + a WARNING in our log | "This meeting link does not work." |
| Setting on, SMS provider down | **no guest can join any meeting** | the 502 above. The mitigation is turning the setting off, which takes effect on the next request |

A bug found and fixed during the work: the "could not send" answer was first `Results.Problem`, whose sentence is in `detail`. The guest web client reads `error` only, so the guest would have seen "This meeting link does not work." Changed to `Results.Json` with `error`.

## 5. Process gaps — proposals, nothing built

### 5a. Isolated developer workspaces

**What happened.** Two Claude Code sessions shared the folder `tatvaos-connect-caps/`. One switched branches under the other. It saved the other's uncommitted work as a WIP commit first, so nothing was lost — by care, not by design.

**Proposal.**

1. **One worktree per piece of work, created by the session that uses it, never reused.** `git -C tatvaOS worktree add ../wt-<branch> -b <branch> origin/main`. Removed after merge.
2. **A claim marker.** A git-ignored file `.session-claim` in the worktree root holding the session id and a timestamp, written on creation.
3. **An enforced check, not a habit.** A Claude Code `PreToolUse` hook in the parent folder's `.claude/settings.json` that inspects Bash commands containing `git switch`, `git checkout`, `git rebase`, `git commit` or `git stash`, resolves the target worktree, and **denies** the call when `.session-claim` names a different session. The denial message names the owner.
4. **Rule text** for `docs/HOUSE_RULES.md`: "A worktree belongs to the session that created it. Never change branch in a folder you did not create." With today's incident attached, as the rules require.

Cost: small — a hook script and four lines of rule. What breaks if enforced: a crashed session leaves a stale claim; the hook should ignore claims older than 24 hours. Needs Mr. Singh's approval because it adds a rule.

### 5b. No deploys during a flagged live customer meeting

**What happened.** Nothing in the deploy path knows a meeting is running. A deploy recreates the API and web containers (about a minute: joins, waiting-room admits, host controls and captions fail; webhooks may be lost). The media server is recreated only when its image or config changes.

**Proposal, two layers.**

1. **A flag a person sets.** Platform setting `deploy.hold_until` (timestamp) with a reason, set from the operator console — "Company meeting, hold until 19:30". `deploy.sh` reads it **first** and refuses while it is in the future, printing the reason. Override only by a workflow input `override_hold=<reason>`, which is written to the run log.
2. **A measured guard, so it does not depend on someone remembering.** Also in `deploy.sh`, before any container is touched: count meetings with `status='active'` that have a participant `last_seen_at` within the last 2 minutes. If any, print the count and the largest room and refuse, with the same override. For a meeting flagged important, additionally refuse from 15 minutes before its `scheduled_start`.
3. `verify-live.sh` unchanged.

**What would prove the guard works:** a local run with one active meeting row and a fresh `last_seen_at` must exit non-zero before any `docker compose` line; with the override, it must proceed and print the reason. House rule 12 applies: it prints `[ok]` only after it has actually queried.

**What breaks if enforced:** an abandoned meeting with a stuck `active` status blocks every deploy — hence the 2-minute `last_seen_at` condition and the override. **This changes `deploy.sh`, one of the four gated files: it is Mr. Singh's to approve before anyone writes it.**
